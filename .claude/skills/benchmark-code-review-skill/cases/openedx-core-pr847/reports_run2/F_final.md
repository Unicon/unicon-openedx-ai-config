### Detail for each kept finding

**1. Migration conflict and merge conflicts (85).** `git ls-tree main` lists `0014_add_archived_to_criteria_group_and_criterion.py` (from #716, afce3e7) and pr-head lists `0014_criteria_group_unique_constraints.py`; both depend on `0013`. With both files present on main, `python manage.py makemigrations --check --dry-run` and `migrate --check` fail with `CommandError: Conflicting migrations detected; multiple leaf nodes in the migration graph` (CONFIRMED by me in a worktree at main). A no-commit merge of pr-head into main conflicts in `api.py`, `serializers.py`, `urls.py`, `views.py`, `rules.py`, `conftest.py`, `test_api.py`, `test_rules.py`, and `test_views.py`, because `pr-base` is an earlier revision of #846 than what merged. `criteria.py` auto-merges, so main's `archived` field and the PR's `constraints` list sit side by side without manual work; scope 3 regenerated the migration on that merged model and got a `0015` depending on main's `0014`. After the rebase, state explicitly that the `get_or_create` and duplicate check do not yet consult `archived` and that #717 owns that.

**2. Scenario 15 not implemented (70).** The AC reads "the created criterion's rule_profile_id is that taxonomy's rule profile, not the system default". `create_competency_criterion` (api.py:196-202) hardcodes all three scope columns null. With a live taxonomy-scoped profile (id 2) present, a POST with no rule fields returned 201 with `rule_profile_id` 1 (CONFIRMED, probe 10). No test creates a taxonomy-scoped profile before posting, and the commit message's deviation list does not mention it. Two documents support dropping the AC rather than implementing it: ADR 0002's MVP note (line 237) says only the system default exists in this phase, and #672 says "Resolve every profile-referencing criterion against the system default only". Either path is acceptable; silently shipping neither is not, because Decision 4 says the FK is never re-resolved, so a criterion created against the wrong profile keeps the wrong threshold forever.

**3. The read-merge-write can delete other competencies' criteria (65).** `tag_object` deletes every ObjectTag for the (taxonomy, object) pair that is not in the list it is given (`src/openedx_tagging/api.py:429-437`), and `CompetencyCriterion.object_tag` is `on_delete=CASCADE`. The merge list comes from `get_object_tags`, which excludes ObjectTags whose taxonomy is disabled or whose Tag was deleted, while `tag_object`'s own read (`_get_current_tags`, `api.py:323-329`) excludes nothing. Three triggers: (a) with the competency taxonomy disabled, `associate_competency_criterion(tag_id=B, object_id=O)` through the public Python API deleted tag A's ObjectTag and A's criterion (CONFIRMED, probe 07: criteria went from ids [1] to [2] only); through REST the same request is a 403 only because `can_view_object_tag_taxonomy` requires an enabled taxonomy, a predicate in another app. (b) Two concurrent requests for different tags on the same object hold different Tag locks, so nothing orders them; if request B reads `get_object_tags` before request A commits and calls `tag_object` after, A's ObjectTag and criterion are deleted (consequence CONFIRMED by scope 4's deterministic replay; feasibility on two real connections INFERRED, the window is the handful of statements between api.py:190 and the re-read inside `tag_object`). (c) After a sibling Tag is deleted, its orphaned `tag=None` ObjectTag, which `openedx_tagging` preserves on purpose (`models/base.py:667-671`), is deleted by the next POST (CONFIRMED by scope 1). Once learner status exists (main), the cascade becomes a `ProtectedError` 500 instead of silent loss.

**4. Client-supplied rule fields (60).** `rule_profile_id` is a bare `IntegerField` passed straight to `CompetencyCriterion.objects.create`; `save()` runs `full_clean(validate_constraints=False)`, so the xor constraint is enforced only by the database and the view catches only `ValidationError`. Observed (CONFIRMED, probes 01 to 04 and 11): profile plus both overrides is a 500 with nothing persisted; `rule_payload_override` alone is a 500; an archived profile is accepted (201, stored); a profile scoped to another organization's course run is accepted, and deleting that course run then raises `RestrictedError` through `rule_profile`'s RESTRICT, so an author in one organization can make another organization's course run (or an unrelated taxonomy) undeletable; a nonexistent id is a 400 keyed `rule_profile` rather than `rule_profile_id`. `rule_type_override` alone and a malformed payload are correctly 400 via `clean()`. #672 says the frontend never sends `rule_profile_id` and ADR 0002 Decision 4 says the system resolves it, so dropping the field from the request is the simplest fix; otherwise resolve it through `CompetencyRuleProfile.objects.filter(archived=False)` scoped to the system default, the tag's taxonomy, the resolved course run, or that course's organization.

**5. Leaf groups contradict ADR 0002 Decision 2 (60).** ADR 0002 line 86 (column 4 of the group table) reads: "Within a course-scoped subtree, every group carries the same course_id, not only its topmost group; immutable after creation. Root groups always have course_id null." Line 112 defines the retrieval root scope as "all nodes where course_id is null" and line 113 expects that set to stay small. The PR creates every leaf with `course=None` (api.py:146), so under the ADR's own definition every leaf in every course is "root scope". The ticket's Technical Details say "A leaf group never sets course_id", so the ticket (updated 2026-09-15) and the ADR (amended 2026-09-04 for #676) disagree and the PR follows the ticket. The disagreement is baked into data: the unconditional `(tag, course, parent)` constraint only tolerates several leaves under one course-level group because leaves have `course=NULL`, and `resolve_supplied_leaf_group`'s leaf test (api.py:160) is `parent_id set and course_id null`. Fixing this after leaf rows exist means a data migration plus a constraint redesign, so the ADR and ticket owners should decide now.

**6. Root uniqueness by lock only (55).** The schema accepts two roots for one tag; afterwards `get_or_create(tag=tag, parent=None)` raises `MultipleObjectsReturned` and the endpoint returns 500 for every derive-path request on that tag (CONFIRMED, probe 08). The conftest `group` fixture, admin tooling, a shell, a data import, or any future endpoint that forgets the lock can create that state, and the ticket explicitly asked for constraint-backed race safety. ADR 0004 Rejected Alternative 1 records why this project distrusts lock-only correctness ("SQLite has no row locks, so the test suite could not exercise it"). The constraint's `parent` column makes the course-level rule depend on the root rule too: with two roots, two course-level groups per (tag, course) are allowed. Scope 2 also argued that under `ATOMIC_REQUESTS` (set in edx-platform `openedx/envs/common.py:405` and Tutor `auth.yml:16`) the non-locking `get_or_create` reads could miss a concurrently committed root; that holds only under REPEATABLE READ, and Django's MySQL backend defaults to READ COMMITTED, where every consistent read takes a fresh snapshot, so I carry it as a caveat for operators who override the isolation level rather than as the main defect. A MySQL-safe database backstop exists in this very file: a derived non-null discriminator column with a plain `UniqueConstraint`, which is how `CompetencyRuleProfile.scope_code` works; MySQL 8.0.13+ also supports expression indexes (see Gaps for the version question).
