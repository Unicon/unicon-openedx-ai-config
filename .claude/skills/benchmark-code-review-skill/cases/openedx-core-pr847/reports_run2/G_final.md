### Bug

**B1. The branch cannot merge: two leaf migrations numbered 0014.** `src/openedx_learning/migrations/0014_criteria_group_unique_constraints.py:12` depends on `0013`; main's `0014_add_archived_to_criteria_group_and_criterion.py` (#716, `afce3e7`) also depends on `0013`. On `main` plus this change, `python manage.py makemigrations --check --dry-run` and `migrate --check` both fail with "Conflicting migrations detected; multiple leaf nodes in the migration graph: (0014_add_archived_to_criteria_group_and_criterion, 0014_criteria_group_unique_constraints in openedx_learning)", and the CBE suite errors out at test-database setup (22 passed, 190 errors). Renumber to `0015` depending on main's `0014`. (A `--merge` migration also works, which confirms the model state itself does not conflict.)

**B2. The branch cannot merge: the `isolated_apps` contract on `main` is broken.** `api.py:16` `from openedx_catalog.models import CourseRun`. `main`'s `.importlinter` (#861, `cd2b2a0`) allows code outside `openedx_catalog` to import only its `api`, `models_api`, `data` and `tests` modules; `lint-imports` on main plus this change reports "Contracts: 2 kept, 1 broken ... openedx_learning.applets.cbe.api:16: imported from non-public API of openedx_catalog". `models/criteria.py:18` already imports from `openedx_catalog.models_api`; use the same. Rule: `.claude/CLAUDE.md` Architecture, "Respect the layering in `.importlinter`".

**B3. Two supported request bodies return a 500 (`IntegrityError`) instead of a 400.** Reproduced through the view: `{"object_id": ..., "rule_payload_override": {"op":"gte","value":0.5,"scale":"percent"}}` with no `rule_type_override` (R1), and `rule_profile_id` together with both overrides (R2), each raise `IntegrityError: CHECK constraint failed: oel_cbe_criterion_profile_xor_override_check`. Mechanism: `create_competency_criterion` only resolves a default when all three fields are None (`api.py:195-202`); `CompetencyCriterion.save()` runs `full_clean(validate_constraints=False)` (`criteria.py:361`), so the combination reaches the database; `views.py:98-99` maps only `DjangoValidationError`. AC 16 lists these as inputs the endpoint must handle ("by any combination of supplied fields"). Validate the combination in the serializer (`validate()`), before the lock and the tag write.

**B4. Authorization runs before validation, so AC 20's malformed-`object_id` 400 is a 403 for everyone but a superuser.** `views.py:84-87` builds `ObjectTagPermissionItem(taxonomy, object_id=<raw string>)` and calls `has_perm` before `api.py:271` parses the key and `api.py:276` resolves the course. The ticket's Logic orders parse (step 2) and CourseRun (step 3) before permission (step 4) (#665 lines 289-291). The production predicate (edx-platform `content_tagging/rules.py:390` → `can_change_object_tag` → `can_change_object_tag_objectid`) returns False when `get_content_key_from_string` raises `ValueError`, which it does for any string that is not a CourseKey, LibraryLocatorV2, UsageKey, ContainerKey or CollectionKey; it also returns False for a role-less author on a course key that resolves to nothing (`has_studio_write_access` → `STUDIO_NO_PERMISSIONS`), which turns AC 21's 400 into a 403 for the ordinary author the ticket is written for. The repo's tests pass only because `test_views.py:39-44` replaces the rule with a stub that ignores `object_id`. Inferred step: the production predicate was read in the edx-platform checkout, not executed. Fix: parse `object_id` in a serializer `validate_object_id` (400) and resolve the CourseRun before `has_perm`, in the ticket's order.

**B5. Creating a criterion on a disabled competency taxonomy silently deletes the object's other competencies' criteria.** `api.py:190` reads existing tags with `get_object_tags(object_id, taxonomy_id=...)`, which excludes a taxonomy with `enabled=False` (`openedx_tagging/api.py:204`); `api.py:193` then calls `tag_object(object_id, taxonomy, [new value])`, whose `_get_current_tags` does not apply that filter and which deletes every current ObjectTag not in the list ("removes omitted ... tags"); `CompetencyCriterion.object_tag` is `on_delete=CASCADE` (`criteria.py:301-307`). Reproduced: after a 201 for tag A on object X, disabling the taxonomy and associating tag B on X deleted A's ObjectTag and A's criterion, both through `associate_competency_criterion` directly (R8b) and through the view as a superuser (R8c); a non-admin got 403 from the taxonomy predicate (R8), so the reachable actors are taxonomy administrators, which the platform's `change_objecttag_taxonomy` binding (`content_tagging/rules.py:396`) lets through. `enabled` is a first-class Taxonomy setting. Once learner status exists the same path raises `ProtectedError` (500) instead. Fix: refuse a disabled taxonomy in `resolve_competency_tag` (404 or 400), or read the current tags without the `enabled` filter. This is exactly the hazard the docstring at `api.py:179-181` says the merge prevents.

**B6. A competency taxonomy with `allow_multiple=False` returns a 500 on the second competency for an object.** R12: after a 201 for tag A on X, the request for tag B on X raised `ValueError: Taxonomy (Single) only allows one tag per object.` from `openedx_tagging/api.py:326`, unmapped by `views.py:98-99`. `allow_multiple` is a first-class setting, exposed by this module's own `create_competency_taxonomy(allow_multiple=...)` (`api.py:41-48`). Map it to a 400, or reject at tag resolution.

**B7. A library usage key as `object_id` returns a 500 (`AssertionError`).** R6: `{"object_id": "lb:Org1:lib1:problem:p1"}` parses as `LibraryUsageLocatorV2`; `usage_key.course_key` (`api.py:276`) returns a `LibraryLocatorV2`, and `get_course_run` asserts it is a `CourseKey` (`opaque_keys/edx/django/models.py:138`). The platform predicate accepts library keys, so a library editor reaches this. The ticket defers library support (Open Questions), which makes this a 400 to add, not a feature: reject a context key that is not a `CourseKey`.

**B8. Derived group names overflow `name` on MySQL.** `CompetencyCriteriaGroup.name` is `max_length=255` (`criteria.py:79-81`); `Tag.value` allows 500 (`openedx_tagging/models/base.py:58-62`) and `CourseRun.title` 255 (`openedx_catalog/models/course_run.py:131`); `api.py:136` builds `f"{tag.value} (root)"` (up to 507) and `api.py:142` `f"{tag.value} — {course_run.title}"` (up to 758), through `get_or_create(defaults=...)`, which runs no validation. R9: a 300-character tag value produced 307- and 312-character names that SQLite stored silently. Inferred step: MySQL 8's default `sql_mode` includes `STRICT_TRANS_TABLES`, under which the INSERT raises `DataError` → 500, so any competency with a value over 248 characters can never get a criterion on the CI and production database. Truncate or elide to 255, or drop the derived names (the ticket's Open Question says these groups are "never shown in the UI").

**G4. One-root-per-tag is enforced only by a row lock, and a second root breaks every later request for that competency.** ADR-0002 line 72 defines a tree as "one root CompetencyCriteriaGroup plus all descendant groups"; `criteria.py:44` and #675 line 149 and #717 line 62 rely on it. The lock (`api.py:132`, `285`) protects only callers of this code; R11 inserted two roots through the ORM (the constraint allows it, P2) and the next derive-path POST returned 500 with `MultipleObjectsReturned` from `get_or_create` (`api.py:133`), and the course-level constraint stops meaning one group per (tag, course) because each root is a different `parent`. The commit message's "the root group cannot be backed by a constraint" is false: this repository already backs an identical MySQL-limited uniqueness rule with a derived column that is non-null only on the rows that must be unique plus a plain `UniqueConstraint` (`CompetencyRuleProfile.scope_code`, `criteria.py:169-180`, `203-207`; ADR-0002 Decision 3 line 134, Decision 5 line 249, Rejected Alternative 6 lines 420-429). Apply the same pattern (a nullable column that is, say, `"root"` for roots and NULL otherwise, unique with `tag`, plus a `CheckConstraint` tying it to `parent IS NULL`). The lock-only design is also isolation-dependent: it is correct under Django's default READ COMMITTED (P3), but a deployment that sets REPEATABLE READ with the platform's `ATOMIC_REQUESTS` would take its snapshot before the lock wait and create two roots; ADR-0004's Rejected Alternative 1 (lines 88-89) rejected lock-based correctness for that reason. #717's root-reactivation path keeps working with a constraint.

**G5. ### Question

**Q1. Which isolation level does this design assume, and where is that recorded?** The commit message argues from REPEATABLE READ; the product runs READ COMMITTED (P3). The lock-only root design is correct only under READ COMMITTED (G4). If the team keeps the lock, record the assumption in ADR-0002 (Decision 2 and 5), because #717 and #675 build on it.

**Q2. Who adds the `archived` filters, and does the constraint leave room for the result?** `main` already has `archived` on both models (#716). This PR's root and course-level `get_or_create` (`api.py:133-143`), the duplicate check (`api.py:223-238`) and `resolve_supplied_leaf_group` do not filter on it. #717 owns the filters and its reject-not-replace design fits the unconditional constraint, but #717's text assumes "partial UniqueConstraints (one root per competency ...)" and a plain `.exists()` duplicate query; it will have to adapt to the actual constraint set and to the `select_for_update().filter(...).first()` shape here.

**Q3. Should the derive path assign `ordering`?** Every group this PR creates keeps `ordering=0`; ADR-0002 lines 79 and 88 make `ordering` the deterministic sibling evaluation sequence that short-circuit evaluation relies on. With ties everywhere, sibling order is undefined.

**Q4. Where does the permission check live, and which exception type does `api.py` raise?** The view checks `has_perm` (`views.py:85-87`), which matches every other `api.py` in `src/` (none takes a user). #674 (lines 41, 189, 208) and #675 (lines 154, 174, 187) say #665 does an inline `has_perm` inside `associate_competency_criterion`, which is false at head; #675 and #674 also pass a course-key string as `object_id` where this PR passes the usage key. #717 line 110 tells its implementer to raise DRF's `ValidationError` from `api.py`; this PR raises Django's and translates in the view. Record both conventions and update the four tickets.

**Q5. The #666 seam is a comment, not a function.** `api.py:204` "#666 inserts its parent-competency dominance/containment check here"; #665 line 208 reserves `_validate_containment(group, object_id)`; #666 lines 143/153/159 want `_validate_containment(group, parsed_key: UsageKey)` called with the already-parsed key and no signature change to `create_competency_criterion`, which only receives the string. #666 can add the function without undoing anything here, but not under all three of its own constraints; who adapts?

**Q6. #672 line 260 expects the backend to normalize an override equal to the applicable default back into a profile reference.** Neither #665 nor this PR does that (ADR-0002 line 180 describes it for a changed override). Criteria created with an override equal to today's default stop following the default when it changes. Who owns this?

**Q7. Integer ids in the REST contract.** URL `tag_id`, request `group_id`/`rule_profile_id`, response `id`/`group_id`/`object_tag_id`/`rule_profile_id` are all integer primary keys; `README.rst` lines 42-43 reserve `uuid` as the stable external reference and #613 line 153 added `uuid` so REST APIs "are never forced to expose an integer primary key". #665 specifies integers and #846 does the same, so this is not the PR's defect, but switching after #672 ships is a breaking change; record the decision in #681's contract or ADR-0002.

**Q8. Platform ObjectTag deletion cascades into CBE rows.** The platform deletes ObjectTags on `XBLOCK_DELETED` (`content_tagging/handlers.py:20-28`) and on CSV import; with `CompetencyCriterion.object_tag` CASCADE that removes the criterion and leaves an empty leaf (ADR-0002 line 110), or raises `ProtectedError` once learner status exists (ADR-0002 Decision 7 line 309 wants archiving). Not this PR's to fix, but this PR creates the rows; which ticket (#674, #613) owns it?

**Q9. A leaf's tag and course are checked only on the supplied path and only against the leaf and its parent** (`api.py:162-165`); nothing in the database ties a leaf's tag to its root's. #675 line 149 assumes one tree per tag. If G5 goes toward leaves carrying `course_id`, the course half becomes a checkable denormalized value.

### Suggestion

**S1. Remove the locking reads at `api.py:223` and `:228`** and reword the comment at `:222`. The `Tag` lock at `:285` already serializes same-tag callers; under READ COMMITTED a plain read after the lock sees the competitor's commit (P3), and under REPEATABLE READ they would gap-lock an empty `ObjectTag` range that `tag_object` then inserts into, which is a deadlock hazard between requests for different tags on the same object, not a protection.

**S2. Remove the nested `transaction.atomic()` and second `Tag` lock in `create_leaf_group` (`api.py:129-132`)** once the function is private (G12); when called from `api.py:290` they are a savepoint and a re-lock of a row the caller already holds.

**S3. Remove the two mock-based lock tests** `test_api.py:295-305` (`test_create_leaf_group_locks_the_tag_row_before_creating_groups`) and `test_api.py:438-465` (`test_associate_competency_criterion_locks_the_tag_row_before_the_duplicate_check`). They assert that `select_for_update` was called, or in what order; BR24 replaced the lock with an unevaluated queryset and all three parametrizations still passed, and SQLite ignores `FOR UPDATE` anyway. With a database constraint for the root (G4) an `IntegrityError` test replaces them.

**S4. The autouse fixture `test_views.py:39-44` replaces `oel_tagging.change_objecttag_objectid` for the whole process and never restores it.** The precedent at `tests/openedx_tagging/test_views.py:713` does the same, which is why this is a Suggestion rather than a Gap; a yield fixture that restores the previous predicate removes the order dependence (the full suite currently passes: 1106 passed, 1 skipped).

**S5. `resolve_competency_tag` runs twice per request** (`views.py:84`, `api.py:265`), three queries each (R13 counted 34 non-savepoint queries on the derive path). Accept the resolved tag, or resolve once.

**S6. Assert the negative clauses the criteria state**: AC 4 and AC 11 "no CompetencyCriterion is created", AC 7 "no CompetencyCriteriaGroup rows are created" (the AC 12 test does assert this); AC 8's view test covers only a root (the api test covers course-level).

**S7. The rollback test (`test_api.py:518-534`) should also assert the ObjectTag rolled back**, since `tag_object` writes before the criterion insert.

**S8. `create_leaf_group`'s docstring "one per criterion" (`api.py:120-123`) states a cardinality the model does not have**; a supplied `group_id` attaches many criteria to one leaf (R13, AC 12).
