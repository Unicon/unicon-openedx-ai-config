# [Follow-up - BE] Reject a competency taxonomy import that re-arranges tags into a dominance conflict

GitHub: pending
Cached: 2026-10-23

## User Story
As an administrator, I want a re-import of a competency taxonomy to be rejected when it would re-arrange tags in a way that breaks the competency dominance rule, in order to keep the competency criteria already configured for courses across the platform valid and manageable in Studio.

## Description

*Competency Dominance Rule Definition*: No ancestor/descendant pair of competency tags may both hold live criteria in the same course.

Each taxonomy reports a taxonomy_type. In the event that the taxonomy_type is Competency, then when re-importing this taxonomy, it needs to fail if someone tried to re-arrange the tags in a way that violates #666, and the import should report back the error in a useful way to the end user. In order to continue following the rule that the tagging code is not allowed to know about the CBE code, we will implement this using the same principle described in ADR 0013 which suggests using openedx-platform as a proxy to handle the relationship between tagging and CBE. We will have openedx-platform pass a CBE validator function into the tagging import function when the taxonomy is a competency taxonomy. The tagging code runs it during the plan phase, after its own validations, and reports all errors together, on both the preview and the real import.

## Notes for drafting

Everything below was settled in the 2026-10-23 session with the architect (mgwozdz) and is background for the BA's draft pass. It is not posted.

**Priority and framing (architect's take).** This loophole has been known for about a week or so, but the architect deferred it as an MVP edge case: re-importing a taxonomy in a way that breaks your own competency configuration is not something a reasonable admin sets out to do. Jesper's 2026-10-21 comment on #683 (a competency with criteria gained a child through a taxonomy edit, after which #666 blocked the child's associations in that course and the author couldn't see why) prompted writing the ticket now. It is labeled "Follow-up" because it surfaced too late to make any current Epic 5 deadline, so it is lower priority than the rest of the epic and should be sized and written as a standalone follow-up. Jesper's frontend-only suggestion was declined. The frontend half of his report (non-leaf competencies not selectable) was a bug introduced in frontend-app-authoring PR #3275, already commented on by the architect; no new frontend ticket is needed.

**Product rule (architect's decision).** A competency at any level of the taxonomy can carry criteria. The only limit is #666's dominance rule: no ancestor/descendant pair may both hold live criteria in the same course. Leaf-only is not a rule anywhere. Archived criteria and archived associations never block anything.

**Which hierarchy changes can violate #666.** Adding a new child tag (interactive add sub-tag, or import create-with-parent) can never violate it, because a new tag has no criteria. Only reparenting an existing tag can, which import does through its `UpdateParentTag` action (`src/openedx_tagging/import_export/actions.py`). A move changes the ancestry of the moved tag and its whole subtree, and gives the new ancestors new descendants, so the check must cover every tag whose ancestor or descendant set changes, with all moves in the file applied together, not each move alone. The Django admin's Tag form also edits `parent` directly and bypasses all of this; the architect accepts that gap.

**Chosen approach (architect's proposal, confirmed).** openedx-platform is the proxy, the same pattern ADR 0013 (`docs/openedx_tagging/decisions/0013-competency-taxonomy-detection.rst`) uses for `taxonomy_type`: `openedx_tagging` must never know CBE exists (`.importlinter` comment). Shape:
- `openedx_tagging.import_export.api.import_tags()` gains one generic, optional parameter: a list of extra validator callables run during the plan phase, after tagging's own action validation, whose errors are appended to the plan's error list. Same shape as Django's `validators=[...]` on fields. No CBE reference in tagging.
- Platform inherits `update_import` and `plan_update_import` from core's `TaxonomyView`, and both call `import_tags()` directly, so platform has no place to pass anything in today. Core's `TaxonomyView` therefore gains an overridable hook (for example `_get_import_validators(self, taxonomy)`) that returns no validators by default and is called by both of those actions, mirroring the existing `_create_taxonomy_for_import` hook platform already overrides. openedx-platform's `TaxonomyOrgView` (`openedx/core/djangoapps/content_tagging/rest_api/v1/views.py`) overrides it to return the CBE validator when `openedx_learning.api.is_competency_taxonomy(taxonomy)` is true. `create_import` (new taxonomy by import) is out of scope: a new taxonomy has no criteria, so the check can never fire there. The re-import and plan request bodies carry no `taxonomy_type`, so the gate is that function on the stored taxonomy. Platform master already has the ADR 0013 wiring (platform PRs #39086 and #39110, merged September 2026), so this builds on merged code.
- A new CBE public function in `openedx_learning` takes the `TagImportPlan` and returns #666-style errors: for each affected tag, compute its proposed ancestors and descendants from the plan, then reuse `get_courses_with_relative_criteria(tag_ids, course)` from PR #875 (#666) to find conflicting courses. `get_ancestor_tags` / `get_descendant_tags` from #875 don't reuse directly because they read the stored `lineage` of each `Tag` row, and the check must run against the tree the file would produce.
- Each dominance error is an `ImportActionError(action=<that tag's UpdateParentTag>, message=...)`, so it renders like tagging's own errors ("Action error in 'update_parent' (#N): ...") and points the admin at the file row. The message names both tags of the conflicting pair (the ancestor and the descendant, which may be the moved tag itself or a tag that didn't move), the course key, and a one-line remedy (leave the tag where it is, or archive or remove one competency's criteria in that course first). Every conflict is reported, not just the first per move. The course key is always named, even when the importing admin can't access that course. #666's own message (one tag plus course) can only be followed loosely.

**Design details settled with the architect agent's pre-handoff findings (2026-10-23).**
- Validator signature: `Callable[[TagImportPlan], list[ImportActionError]]`. Validators are read-only (the plan-only call promises no writes), return errors rather than raising (a raised exception lands in `import_tags()`'s broad `except` and loses the whole plan from the preview), and run even when tagging already found errors, so they must tolerate a parent tagging couldn't resolve.
- Placement: validators run after `generate_actions()` and before `task.log_plan()` in `import_tags()`. `log_plan` copies the plan and its errors into the task log at that moment; a validator that runs later would still block execution but its messages would never reach the log the wizard shows.
- Proposed tree: computing it from `UpdateParentTag` actions alone is not enough. Tags created in the same file can be links in the ancestry (A has criteria in X; the file creates N under A and moves B, which has criteria in X, under N), and replace mode deletes and root-promotes tags the file omits, so the final tree has to account for every row plus every surviving existing tag. Tagging already owns this computation in PR #877 (Seva, `ufedaseyeuconsultant`, open as of 2026-10-23, "reject stale parent_id in tag import and make parent changes order-independent"): `TagImportPlan._end_state(tags, existing)` in `import_plan.py` returns three dicts keyed by casefolded final external id: `parent_of` (parent's final id or None), `pk_of` (existing pk or `NEW_TAG`), and `row_of` (0-based file row, shown as "Row N" in errors). It runs after the delete and staging actions are built and already handles replace mode, renames (`previous_id`), and tags the file never mentions. This ticket reuses that result rather than adding a second tree computation: the plan keeps the end state (or exposes it through a small public accessor) so a validator can read `parent_of` and `pk_of` without re-deriving tagging's rules. The stored tree for the "before" side comes from each existing tag's current `parent` (one query). This ticket therefore depends on PR #877 merging, in addition to PR #875. #877's follow-ups #892 (parent errors name their row and report every cycle) and #893 (reject a parent_id the full replace import deletes) are Seva's and don't change this ticket's shape, but the error convention here should match theirs (row-based references).
- Which tags to check: only pairs the import newly creates. The moved set is every existing tag whose proposed parent differs from its stored parent and is not root (a move to root only removes ancestors). For each moved tag m: new ancestors = proposed ancestors minus stored ancestors; subtree = m plus its proposed descendants. Both sets come from the final tree, so whole-subtree moves, several moves in one file, and tags another move puts under m are all covered. Pre-existing violations never block an import.
- Reuse: `get_courses_with_relative_criteria(tag_ids, course=None)` from PR #875 returns one tag per course (lowest id), so a single call over all affected tags can't find a pair. Call it twice per moved tag, once with the new ancestors and once with the subtree, and intersect the courses; for each shared course the two returned tags are a genuine ancestor/descendant pair. Its filter already skips archived groups and criteria, which is the settled rule. Two queries per moved tag, none when nothing moves under a new parent. Query strategy beyond that is the implementer's.
- Parent cycles: PR #877 adds `ParentCycleError` and rejects a file whose parent_id would make a tag its own ancestor (reported once, on its first row), along with trees deeper than the taxonomy limit, in `_validate_hierarchy()`. Since this ticket runs after that validation on the same end state, a cyclic tree never reaches the validator; a visited set in the ancestor walk is cheap insurance, not a requirement. The cycle bug the architect agent found by code reading is therefore Seva's, already in flight, and out of scope here.
- Race: the real import re-plans and re-runs the validators, so a criterion created between preview and import is caught. The remaining window is inside one `import_tags()` call, between the validator's reads and the atomic execute's commit. Accepted and stated in Technical Details; PR #875's own `_validate_containment` has the mirror-image race and locks only the criterion's tag and course run.
- Public API: a trailing optional `validators=None` keyword on `import_tags()` is additive, no DEPR. `import_tags` is not re-exported from `openedx_tagging.api`; its only callers are tagging's views and an unused Celery wrapper. The new CBE function is additive and goes in `openedx_learning.api.__all__`. No ADR: documented in the docstring and Technical Details.
- Release order: PR #875 and PR #877 merge, then this openedx-core PR, then an openedx-core release, then the openedx-platform PR.
- Restore: no restore path for an archived criterion or group exists or is planned, so there is nothing to guard; Technical Details states that restore is out of scope and would need its own dominance check if ever added.
- Parse errors stop the import before planning, so "all errors reported together" means plan-level errors only.
- Replace-mode deletes promote surviving children to root before deletion (`import_plan.py`), which only removes ancestors and can't create a pair; archiving-vs-deleting those tags is #780's boundary, out of scope here. Both #780 and #814 were still open on 2026-10-23.
- Context additions for Technical Details' Additional context (the architect chose not to add these to Context): PR #875 is the blocker whose lookup this reuses; #796 is the closer sibling to #666 (shares its course lookup) and #797 is its frontend; #666's own out-of-scope list ("taxonomy parent/child structure changes after criteria already exist") is exactly the gap this ticket closes.
- Verified: Studio's import wizard shows the task log on both the preview 400 (`ImportTagsWizard.jsx`, error alert, Next disabled) and the real import 400, so no frontend change.

**Why the seam is inside `import_tags()`.** Preview and real import are separate HTTP calls, but the real import plans and executes inside one `import_tags()` call with nothing between plan and execute. A platform-side check before the call would need a plan-only pass first, re-parse for the real run, and would never show the CBE errors in the real run's task log. Validators run during the plan phase cover both calls in one place, and Studio's import wizard (`src/taxonomy/import-tags/ImportTagsWizard`) already displays the plan's error list and task log, so no frontend change is expected (inferred: wizard call order verified, error rendering not traced in detail).

**Decisions from the pre-handoff check**
- Archived criteria and associations never block a reparent.
- Archived child tags: moot, since leaf-ness no longer matters.
- Django admin gap: accepted.
- Pre-existing violating data (e.g. Jesper's test env): not this ticket's problem.
- Epic placement: Epic 5 (#721), where #666 lives; Epic 10 (#723) was the alternative.
- One ticket with PRs in both repos, not a per-repo split.
- The check flags only ancestor/descendant pairs the import newly creates.
- Platform hands the validator over through an overridable hook on core's `TaxonomyView`, not by overriding the actions or via a Django setting.
- The proposed-tree computation is a generic method on `TagImportPlan` in tagging.
- No ADR for the validator seam; docstring and Technical Details only.
- User Story actor becomes the taxonomy administrator, with course authors' criteria staying valid as the outcome (architect rewrites it).
- Error content: action number, both tags of the pair, course key, one-line remedy. Every conflict reported. Course key always named.
- The plan-to-execute race is accepted and stated.
- `create_import` (new taxonomy) is out of scope.
- The tag-cycle bug is fixed by PR #877 (Seva), with follow-ups #892 and #893; out of scope here.
- The proposed tree is read from PR #877's `_end_state` result, not computed again; PR #877 is a dependency alongside PR #875.
- No restore path for archived criteria exists or is planned; nothing to guard.
