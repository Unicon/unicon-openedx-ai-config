# [BE] Prune criteria groups emptied when tagging code deletes a criterion's association

GitHub: pending
Cached: 2026-10-20

## User Story
As a course author, when I delete a subsection, or a competency tag is otherwise removed from content outside the Competency Management page before any learner has been graded on it, I want the competency rule that pointed at that content to be removed the same way it would be if I had removed it on the Competency Management page, in order to never leave behind an empty criteria group that makes the competency impossible to earn in my course without telling anyone why.

## Description
A competency criterion points at an ObjectTag to connect it to a subsection. The ObjectTag cascades on delete, but it will only cascade delete the criterion, not the parent CompetencyCriteriaGroup. This can happen when Studio deletes a block or a course re-import re-sets a block's tags. When these deletes happen, the group that held the criterion is never checked, so it can be left as an orphan with no criteria at all. In this ticket, we need to make a criterion deletion from any path run the same upward pruning that #674 runs when a criterion is removed on the Competency Management page in order to delete these extra orphaned CompetencyCriteriaGroups.

At a high level:

```
the CBE applet registers a listener for Django's built-in post_delete signal on its own criterion model
  (Django fires this signal for every criterion row it deletes, including rows removed by a cascade from a tag association, so tagging code stays unaware of CBE and nothing new is emitted)
when the listener fires:
  walk upward from the deleted criterion's group using #674's existing pruning: a group left with no live criteria and no live child groups is deleted, or archived if a learner has a recorded status for it, and the walk continues to its parent
```

## Context
- #674 implements the upward pruning for a criterion removed on the Competency Management page.
- #779 makes every tagging-layer delete path archive an association that learner mastery depends on and hard-delete the rest. This ticket covers what the hard-delete branch does to the criteria on that association.

## Notes for drafting

- Verified facts (2026-10-20): `CompetencyCriterion.object_tag` is `on_delete=CASCADE` (`cbe/models/criteria.py` ~286-292). `StudentCompetencyCriterionStatus.criterion` is `on_delete=PROTECT`, so a cascade onto a criterion with learner status raises `ProtectedError`; after #779 that case no longer arises from tagging code, because the association is archived instead. No `post_delete`, `pre_delete`, or `@receiver` exists anywhere under `cbe/` today.
- Tagging-layer paths that hard-delete associations, all in or called from `src/openedx_tagging/api.py`: `delete_object_tags()` (a bulk queryset `.delete()`, `api.py` ~285-291, no taxonomy filter), called by openedx-platform's `content_tagging/handlers.py` `delete_tag_xblock` on `XBLOCK_DELETED` and by `content_tagging/api.py` `set_exported_object_tags()` on course import; `tag_object()`'s reconcile step; `copy_tags()`. #784 hides competency-tag removal on the Course Outline, so block deletion and re-import are the realistic triggers.
- #674's helper in PR #879: `_cascade_from_group(group, event)` in `cbe/api.py`, recursive on `group.parent`, returns early if the group has any live criterion or child group, hard-deletes on a "delete" event unless a `StudentCompetencyCriteriaGroupStatus` row exists (then archives), archives when only archived children remain. `delete_competency_criterion` calls it after `criterion.delete()`. Reuse it; do not duplicate it.
- Re-entrancy to design for: #674's own hard-delete path removes the now-unused `ObjectTag` by calling `tag_object()` without that tag value, so any hook on criterion deletion also fires during #674's own flow (the criterion is already gone by then, so the hook sees no criterion, but confirm it is harmless and does not double-process).
- Mechanism candidates for the architect pass: (A) a `post_delete` receiver on `CompetencyCriterion` in the cbe applet; Django's deletion collector sends `post_delete` for every cascaded row when a receiver is connected, and skips its fast-delete shortcut for that model, so a queryset `.delete()` on `ObjectTag` reaches it. (B) a custom `on_delete` callable on the foreign key that prunes before cascading. (C) overriding `CompetencyCriterion.delete()`, which queryset cascades bypass, so it does not cover this case. Expected recommendation: A.
- Verified 2026-10-20, evaluation side: the merged leaf-status PR #862 records only a criterion's own status and never evaluates groups. The group rollup is PR #870 (open, not merged, so this is its current draft): it reads existing status rows and does not compute AND/OR over a group's children, so an empty group has no rows and is skipped, neither satisfied nor failed; a competency with nothing beneath it logs a warning that it "has no criteria beneath it and can never be demonstrated". No crash, no wrong status, just a competency that cannot be earned in that course.
- Verified 2026-10-20, display side (#672's two PRs, openedx/frontend-app-authoring#3275 and the fork PR AShatsila/frontend-app-authoring#1): a group with zero criteria renders its "By completing any/all" header with an empty body; the criterion list component returns null on an empty list with a comment that empty groups are "not expected for a persisted box per ADR 0002"; no remove control exists in that view. #672 is effectively done and cannot take a follow-up.
- Why this is not the same as the author removing a criterion: #674's path prunes the group when its last criterion goes. The cascade path does not, so only the cascade path can produce an empty group. A group thinned but not emptied by the cascade matches what #674 would do and is not a defect.
- Out of scope: any frontend change; changing #779's archive-or-delete rule; #826's unresolvable-criterion display; pruning groups emptied by paths that already prune (#674, #675).

Decisions from the pre-handoff check (2026-10-20):

- Priority: core, blocked on PR #879 (#674) merging and, for the graded case, on #779 and #782. Not NTH. Estimate about one developer-day.
- Trigger scope: only a criterion deleted by a cascade whose delete originated on an ObjectTag. Django passes the originating instance or queryset as the `origin` argument of `post_delete`; the listener acts only when that origin is an ObjectTag (prior art: `_is_explicit_tag_delete` in `src/openedx_tagging/signal_handlers.py` ~17-39). A delete that originates on a criterion (#674), a group subtree (#675), a Tag, or a CourseRun is ignored, so #674's own flow is a true no-op: its `criterion.delete()` has a criterion as origin, and its later `tag_object()` call only runs when no criterion, archived ones included, still references the ObjectTag, so nothing cascades. Verified: without this filter the listener would fire inside #674's `criterion.delete()` before #674's own walk, which would then read `group.parent` on an already-removed row and raise `DoesNotExist` (not caught by #879's `except (ProtectedError, IntegrityError)`).
- Mechanism: a `post_delete` receiver on `CompetencyCriterion`. Verified against installed Django 5.2 `deletion.py`: `post_delete` is sent once per deleted row including cascaded rows and queryset deletes (~497-512); all criterion rows in a batch are deleted and signalled before the ObjectTag rows are deleted; the collector runs deletes and signals inside `transaction.atomic(savepoint=False)` (~454), so pruning commits or rolls back with the tagging delete and a half-pruned state cannot occur. `CompetencyCriterion` is never fast-deleted anyway (PROTECT from learner status, and simple-history already listens). `post_delete` has no `raw` argument and fixtures never delete, so nothing to guard. Rejected: custom `on_delete` callable (runs during collection before rows are gone, relies on Collector internals); overriding `CompetencyCriterion.delete()` (queryset cascades bypass it); a new event emitted by tagging (new tagging contract just for CBE); `transaction.on_commit` (commits the empty group first, needs per-transaction state).
- Failure handling: run the pruning in a savepoint; on any error, log a warning and leave the empty group (today's state). Never let a pruning error fail the tagging delete. Verified why: Studio sends `XBLOCK_DELETED` via openedx-events `send_event`, which defaults to `send_robust=True` in production (`openedx_events/tooling.py` ~168-178), and the event is fired via `on_commit_changes_to` after `delete_item` in `xmodule/modulestore/mixed.py` ~871-882, so the block is already gone; a propagated error would be logged, not raised, and would roll back the whole tagging delete inside the collector's atomic block, orphaning the block's ObjectTags and criteria.
- Upward walk: reuse #879's `_cascade_from_group(group, "delete")` unchanged, imported as a private helper from a sibling module in the same applet (no need to make it public). Continue to the shared root and remove it only when it has no children left, matching #674; a group with its own `StudentCompetencyCriteriaGroupStatus` row is archived, as the helper already does. Several criteria deleted in one bulk delete produce one listener call per row: handle per row, re-fetch the group by id, stop if it is gone (a batch is one block's tags, so no dedupe state needed).
- Re-import stays a trigger. Tag re-import hard-deletes and re-creates each block's associations (`set_exported_object_tags()` calls `delete_object_tags()` per block, all taxonomies), which already deletes every ungraded criterion today; with this ticket their emptied groups are pruned too. The rule loss itself is not this ticket's problem: it gets its own NTH Epic 11 ticket (cache file `ucid-11.xx-ghi-pending.md`) for making tag import reconcile per taxonomy instead of wipe-and-recreate.
- Author observes: the emptied group disappears from the Competency Management page and the page shows the true state (including the zero-group empty state from #671/#672 when nothing is left), plus a log line. No notice to the author (frontend, out of scope). `CompetencyCriteriaGroup` already has simple-history, so the removal is on record.
- Out of scope, confirmed: CourseRun deletion (its CASCADE onto course-level groups can leave an empty root; the listener must not error during that cascade; a separate ticket if course-run rows are ever deleted in practice, which is unverified); backfill of groups already empty before this ships (CBE has not shipped, only dev and sandbox data); feature flag (none); any frontend change; #826's display of a graded criterion whose subsection was deleted (visibility follows whether learners depend on the rule, the same line #779 draws; accepted).
- Coordination note for Context: #675 and #817 hard-delete ObjectTags inside their own flows (#675 if it removes ObjectTags before its subtree criteria; #817 because its in-use check counts only non-archived criteria). With the origin filter those deletes originate on an ObjectTag and would fire the listener; those tickets should delete criteria first and expect the listener to be a no-op.
- (implementer) Listener placement: a new `cbe/signal_handlers.py` connected from `LearningConfig.ready()` (prior art `src/openedx_content/apps.py` ~46-51); not in the models module, which would create a circular import with `api.py`.
- Evaluation nuance for the AC (inference from the unmerged rollup PR #870): its child-combining step does not skip an empty child group; it counts it as a child with no status, so under an AND parent that parent can never reach Demonstrated, and under an OR or null parent it can never reach AttemptedNotDemonstrated. The business analyst read the same draft as skipping the group. Verify against #870 once merged before stating the harm in the AC.
- Research for the draft pass: none outstanding beyond the #870 verification above.
