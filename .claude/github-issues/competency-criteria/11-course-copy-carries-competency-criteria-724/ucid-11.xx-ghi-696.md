# [NTH - BE] Include Competency Criteria in Course Import

GitHub: https://github.com/openedx/openedx-core/issues/696 (#696, OPEN)
Cached: 2026-10-20

## User Story
As a course author, when I import a course, I want the import to include the competency mastery rules (competency criteria groups and competency criteria) attached to the course's content, in order to recreate them without rebuilding each rule by hand.

## Description
Today, when a course is imported in Open edX, its content tags are included (as `tags.csv`), but the competency criteria groups and competency criteria associated with those tags are not. We should update the import process to also read the JSON file describing this course's criteria groups and criteria, and reconstruct them for this new course.

## Context
- #695 is the corresponding ticket for export

## Notes for drafting

Decisions from the pre-handoff check (2026-10-20):

- Input contract: the file #695 writes, exactly as recorded in #695's notes. References only (taxonomy `export_id` plus tag `external_id`, with value for readability; content by block type plus block id; root group as attach point with its logic operator; nested course-scoped groups with name, ordering, logic operator, competency; rule profile as default-reference-plus-values or override verbatim; integer schema version). Import must keep reading every older schema version.
- Parity with tag import, and where it stops: tag import creates neither taxonomies nor tags; a missing taxonomy or value becomes an ObjectTag with no Tag link. A criteria group's competency is a required foreign key to a real Tag row (`criteria.py` ~64-70) and ADR 0002 limits criteria to competency-enabled taxonomies, so a criterion can never be kept as an orphan. The ticket states this parity and this limit.
- Unresolvable reference (taxonomy missing or not competency-enabled, tag missing, block absent, ObjectTag absent or orphaned, or ObjectTag archived): skip the row and log it, drop any group left empty (ADR 0002 forbids empty groups), skip a whole competency whose Tag is missing. Never attach a criterion to an orphan or archived ObjectTag. The file's Tag, found by `export_id` plus `external_id`, must be the Tag on the ObjectTag that `tags.csv` import created; a mismatch (for example after a rename) is skipped and logged, with no fallback to matching by value.
- Destination already has criteria (re-import): merge with deduplication, one find-or-create algorithm for both fresh import and re-import. Per competency: find the course-level group by competency and course run, else create it under the root. Per bottom-tier group: find the sibling with the same ordering under the matched course-level group, else create it; more than one match means skip and log. Per criterion: skip if the matched group already has a live criterion on the same ObjectTag, else create it. Nothing on the destination is edited or removed. A surviving criterion or group the file also describes with different fields is skipped and the difference logged, never updated, because a survivor has learner status by construction and updating it changes recorded mastery. Repeated import gives the same result. A same-instance import beside a live source finds nothing (lookup is per course run) and behaves like #694. Architect's estimate: about one day more than skipping the file when groups exist.
- State after tag import on a re-import, which #696 inherits: #779 (draft on the architect's docs/779-update branch, newer than the cached copy on this branch) makes every ObjectTag delete path, including tag import's `delete_object_tags()` call, archive an association that learner mastery depends on and un-archive it in place when the import still carries the tag. An association with no learner mastery is still hard-deleted (approach approved on #655), and `CompetencyCriterion.object_tag` is `on_delete=CASCADE` (`criteria.py` ~286-292), so its criterion is deleted with it. So when #696 runs, the destination has every group and every criterion with learner status, and has lost every criterion without one; the merge refills those from the file. #779 and #778 (archived-row read filter) are dependencies for the re-import case; without them tag import raises `ProtectedError` (`StudentCompetencyCriterionStatus.criterion` is PROTECT) and the import task fails with the generic unknown-error message before #696's code runs. A fresh import needs only #613 and #695. No new ticket for the tag-import delete path.
- A criterion whose association stays archived because the import no longer carries that tag: not #696's concern. The same state arises when an author removes the tag in Studio, so the guardrail series owns it. #696 only never matches or attaches to an archived association.
- Rule profile on import: an override imports verbatim; an override that fails the target's validation is skipped and logged. A criterion exported as "uses the system default" plus the default's values gets the target's default when the target's values match the exported ones, otherwise an override carrying the exported values so the rule keeps its threshold (mirrors ADR 0002 Decision 4 trigger 4).
- Root group: attach under the live root for the competency. If none exists, create it with the exported logic operator. If the operators differ, keep the target's and log it; never overwrite, since the root is shared by every course teaching that competency. (implementer) More than one live root means skip that competency and log.
- Learner status: import never creates, changes, or deletes learner status rows. New criteria have no status until the next grade event.
- File problems: a missing file is a no-op. A malformed file or a schema version newer than the importer supports is skipped whole with a warning log, and the course import succeeds, matching how tag import tolerates a missing or malformed `tags.csv`. Unexpected errors propagate to the import task's generic error.
- Transaction: one `transaction.atomic()` for the whole criteria file in the library function. Skipping a row is not a failure. This matters because `import_tags` has no transaction of its own (verified, `xml_importer.py` ~593-600).
- Placement and trigger: one ticket, two PRs. openedx-core gets a new public function on `openedx_learning.api` taking the destination course key and the raw file contents; it owns parsing, version check, reference resolution (through `openedx_tagging.api` only), empty-group pruning, root handling, rule-profile resolution, and the transaction. openedx-platform gets a hard-coded call in `CourseImportManager` right after `import_tags`, inline and synchronous like tags: the ObjectTags exist, the extracted archive is still on disk, and the call is already inside the import Celery task. Not a `COURSE_IMPORT_COMPLETED` receiver (payload carries only the course key; #694 used a receiver only because a rerun has no file and no hook). New entry point, not #694's function, which copies rows that already exist in the database; reuse #694's conventions (creation order, `bulk_create_with_history`, live rows only). Additive, so no DEPR; `.importlinter` already layers `openedx_learning` above `openedx_tagging` and `openedx_catalog`. No ADR; import semantics go in the format doc #695 adds.
- (implementer) Validation: `bulk_create` skips `save()`, where these models call `full_clean()` (`criteria.py` ~344-347), so build rows directly and call `validate_rule_payload` and the tree checks explicitly.
- Defaults, not objected to: author sees nothing in the import UI, logs only, documented in #652; no feature flag (tag import has none); permission is course import only, as in #694.
- Estimate: both experts put this above 1-2 days. Architect: 3-4 days total with merge (2.5-3 openedx-core, 0.5-1 openedx-platform), assuming #695 has landed.
- Research for the draft pass: does a `CourseRun` catalog record exist for the destination right after `import_tags`, both for a Studio import into a new course and for the `import` management command (publish signals may be deferred inside `bulk_operations`)? `CompetencyCriteriaGroup.course` needs that row; #694 creates it if missing.
- Known risk outside #696, flagged to the architect 2026-10-20: the ObjectTag-to-criterion cascade fires on every `delete_object_tags()` caller (Studio block delete, re-import of an archive with no criteria file), leaving groups empty or AND groups missing members, and #674's upward cascade does not run on a database-level cascade. The guardrail series needs an owner for this; #696 only refills what its file describes.
