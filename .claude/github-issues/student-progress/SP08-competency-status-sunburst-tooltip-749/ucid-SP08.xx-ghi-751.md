# [FE] Sunburst Tooltips

GitHub: https://github.com/openedx/openedx-core/issues/751 (#751, OPEN)
Cached: 2026-09-21

## User Story
As a learner, when I hover my mouse over the sunburst, I want to see more information about what this segment represents in order to understand what I need to do to demonstrate mastery of it.

## Description
This ticket will implement the tooltips for the sunburst built in #747. There are 2 cases of tooltips:

Tooltip for Competency Tag segment:
- Display the competency tag name
- Display the competency status just like how it looks in the card header rows
- Display the icon and count of subsection assignments that go towards this competency in this course in the format "<icon> # ASSIGNMENTS".
- If the criteria requirements cannot be displayed easily in 1 line, display "MULTIPLE REQUIREMENTS". If there is a single clear criteria rule to display, then display it in the format "COMPLETE ANY/ALL AT XX% OR BETTER".
- If there are 12 or fewer corresponding subsection assignments, display an icon for the status of each assignment at the bottom of the tooltip. If there are more than 12 corresponding subsection assignments, then don't display any icons for them in the tooltip.

Tooltip for Subsection Assignment segment:
- Display the subsection assignment icon and the name of the subsection, which should wrap.
- Display the competency criterion status just like how it looks in its card row below

When hovering over part of the sunburst, apply an overlay on all segments of the sunburst except the path from the root of the sunburst to the segment that the mouse is touching.

## Context
- Tooltips are for the sunburst built in #747

## Notes for drafting

- Design of record: the three Figma tooltip frames Phil posted on #750 on 2026-10-01 (competency node 1244-26891, sub-competency 1253-5600, assignment 1253-6531), approved by the architect on 2026-10-15 and awaiting Jenna's approval. Frame 1 (hovering "Communication", ring 1): title, heading-style status oval, checklist icon plus "4 ASSIGNMENTS", "MULTIPLE REQUIREMENTS" styled like the panel's rule line without its icon, a row of four small status icons. Frame 2 (hovering "Written Communication", ring 2): same layout, "2 ASSIGNMENTS", "COMPLETE ANY AT 80% OR BETTER", two icons. Frame 3 (hovering the assignment "Draft a persuasive memo"): checklist icon plus the name, then the "Not Demonstrated" oval, no percent. In all three the card sits to the right of the pointer, and the hovered segment, its ancestors, and its whole subtree stay at full color while everything else in that chart fades. The frames predate Option G (#768, approved 2026-10-08): frame 1's icon row has a hollow-circle icon that is not an Option G icon.
- Per #750, competency statements and the "Needs revision" and "Awaiting evaluation" icons are out of scope: no backend field exists for statements, and neither icon is backed by data.
- Data sources, confirmed against the cached tickets: tag name from #734's card heading or row; competency status from #740's per-tag masked map, rendered as #739's `StatusOval` without a percent; subsection name from #734's named row; criterion status and percent from #739's per-criterion masked map; assignment count and icon statuses derivable from #747's node tree (named rows plus each rule box's hidden count); rule line derivable from #734's groups and rule boxes plus the rule recognizer behind `formatRuleText`. A hidden subsection has no name and no status by design, so its tooltip needs its own text (below).
- #755's `combineThreshold` is not reusable here: it reduces several "or better" rules to the highest value, which is right for one score that satisfies every criterion on one subsection but would overstate a mixed-score ALL group here (Quiz 1 at 75% and Final at 90% would read "AT 90% OR BETTER"). Reuse `formatRuleText`'s rule recognition and percent formatting, not its message. The recognizer will then have three callers (#734, #755, #751), which justifies extracting one shared function in `src/ruleText.js`; whichever of #755 and #751 lands second does that.

### Decisions from the pre-handoff check (2026-10-21)

- Highlight: when a segment is hovered, that segment, its ancestors, and its whole subtree stay at full color; every other segment in the same chart fades. The Description's "path from the root to the segment" wording is to be corrected to match. Only the hovered chart fades; a second sunburst and the legend never fade. Implement the fade as a state-driven `data-dimmed` attribute with CSS lowering `fill-opacity`, not `opacity`, so lit segments keep the exact legend colors and the gap strokes don't change; re-render only when the hovered segment changes.
- Inputs: pointer hover (mouse and pen) plus touch. A tap shows the card and highlight, a tap on another segment switches, a tap outside or Escape dismisses. WCAG 1.4.13 applies: Escape dismisses the card, the pointer can move onto the card without closing it, and the card stays until the pointer leaves it or Escape is pressed. The chart keeps #747's `role="img"` and its segments stay unfocusable. Keyboard navigation is a candidate follow-up ticket: the architect notes it was part of the original vision and someone could argue for it, but every tooltip fact is already text in the cards, so WCAG 2.1.1 is defensible without it (the experts' inference, not an accessibility audit), and keyboard support would add 1.5 to 2 days, remove `role="img"`, and strengthen the case for TanStack Charts in #747's open question. A jsx-a11y lint rule may flag hover handlers without keyboard handlers; that must not be suppressed without approval.
- Two tooltip variants, one content component: the competency variant for card headings, rows, and path rows (frames 1 and 2 share one layout and differ only in data), and the assignment variant for subsections.
- Competency status in the tooltip: always the heading-style oval (`StatusOval` without a percent), at every ring, as frames 1 and 2 show, even where the card renders that tag as a row pill.
- Rule line: the short form ("COMPLETE ANY AT 80% OR BETTER") appears only when the segment has no competency segments beneath it and its tag has exactly one bottom-tier group in this course holding exactly one rule box, the same case where #734's group line already carries the score. The text is the group's all/any (AND reads "all"; OR or null reads "any", so a single-criterion group reads "any", as #734's group line already does) plus the rule in #734's three forms ("or better", "or lower", "exactly"), with the percent formatted as #734 does. Every other case, including any segment with competency segments beneath it (a heading with rows, a path row, an ancestor heading with its own criteria) and an unrecognized rule, reads "MULTIPLE REQUIREMENTS". Messages: six whole sentences (all/any times three comparison forms) plus "Multiple requirements", written in sentence case and uppercased with Paragon's `text-uppercase` as #734 does; never splice translated fragments.
- Count and icons: "# ASSIGNMENTS" counts one per criterion in the hovered segment's subtree, hidden criteria included, which equals the outer-ring segments beneath it. The count always shows the accurate number, however large. The icon row shows one icon per such criterion in the same clockwise order as the segments, each with its criterion's status, hidden ones with the Available icon, and is omitted entirely when the count exceeds 12 (the architect's cap, to avoid a wall of icons; the count line stays). Use an ICU plural for "1 ASSIGNMENT". Mark the count icon and the icon row `aria-hidden`; the text carries the meaning. The icons come from the shared Option G status map that #739 creates; Phil should confirm the frames' hollow-circle icon is replaced by the Option G Available icon.
- Hidden-subsection segment: the assignment variant with the checklist icon and the text "A subsection that isn't visible to you" (a new singular message; #734's "N more subsections..." doesn't read on its own) and no status oval, unless Phil adds a fifth "Hidden" entry to the legend, in which case the tooltip follows that design. On the staff route, which shows every subsection by name, it is a normal subsection tooltip.
- Assignment status in the tooltip: identical to the card row's oval, `StatusOval` with `percentGraded`, so a Demonstrated subsection shows its percent. Ask Phil for a Demonstrated frame to confirm. The assignment tooltip shows no rule line of its own, as frame 3 shows; the rule is one hover up and in the card below.
- Unknown status (a criterion or tag missing from #739's and #740's maps): no oval, as the cards do; the icon matches its segment. Masked statuses need nothing extra: the maps are already masked, and the tooltip never says why a status reads Available.
- Known limitation for #752: the competency oval shows the cross-course status (#740), while the icons and count are this course's, so "Demonstrated" can sit above Not Demonstrated icons.
- Mechanism (with #747's hand-rolled SVG): one controlled Paragon `Overlay` per chart showing a white card (`Popover` with its arrow hidden, or `Card`), targeting an invisible zero-size anchor that the chart moves to the point where the pointer entered the segment; one `hoveredId` state set by event delegation on the `<svg>` (`onPointerOver`/`onPointerOut` reading `data-segment-id` via `closest`) drives both the card and the highlight. Anchor at the entry point, never follow the cursor (a card that follows the cursor can't be hovered, failing 1.4.13). `placement="right"`, flipped near edges and mirrored in RTL; a short hide delay keeps the card from flickering when the pointer crosses a gap. No card and no highlight over the center caption, the legend, or the gaps. The portal keeps the card outside the `role="img"` subtree. If TanStack Charts wins #747's open question, its `renderTooltipBody` renders the same content component from the same pure per-node data; only the interaction layer and highlight are SVG-specific. Needs a bounded lookup before drafting: whether Paragon exports `Overlay`, accepts a zero-size SVG target, renders into a portal, and keeps the card open while hovered.
- Files, following #734's layout: `src/SunburstTooltip.jsx` (new: card content), `src/data/sunburstTooltip.js` (new, pure: lit set, count, icon statuses, rule line), #747's chart component (modified: hover state, overlay, dimming, Escape and touch), `src/ruleText.js` and `src/messages.js` (modified).
- #747 must expose four hooks for this ticket, to be added to #747's Technical Details without building any interaction: segment ids namespaced by kind (`tag-12`, `criterion-12`), because tag ids and criterion ids are separate id spaces, with ids on hidden segments too; `ancestorIds` on each node plus a reference to its source card, row, named row, or hidden criterion; a `data-segment-id` attribute on each segment's path; gaps drawn as strokes so changing `fill-opacity` doesn't alter them.
- Staff viewing a learner: same hook, so the tooltips mirror the staff view's cards; one scenario mirroring #740's staff scenario. Loading and failure need no scenario, because #747 hides the chart in both states. One parity scenario: the tooltip always shows what the card shows for the same tag or criterion, masking included.
- Tests: pure tests for the rule line (all and any; the three comparison forms; two rule boxes; two groups; a heading with rows; a path row; an unknown rule), the count with hidden criteria, and exactly 12 versus 13 icons; render tests for hovering a `[data-segment-id]`, the lit and dimmed attributes, Escape, tap, and the hoverable card.
