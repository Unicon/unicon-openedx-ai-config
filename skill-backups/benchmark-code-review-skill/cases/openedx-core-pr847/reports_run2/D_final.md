## Verdict: request changes

The PR is not mergeable as it stands, for three mechanical reasons (it does not merge into `main`, its migration number collides with one already on `main`, and one import breaks an import-linter contract that landed on `main`), and for three substantive ones: the lock that the commit message presents as the race-safety mechanism does not hold under the platform's `ATOMIC_REQUESTS` setting, one acceptance-criteria scenario (taxonomy-scoped rule profile) is neither implemented nor tested while the PR body claims full scenario coverage, and several accepted inputs reach the database and fail with a 500 instead of a 400. Each has a small fix. The overall shape (view validates and authorizes, `associate_competency_criterion()` owns the domain operation inside one transaction, read-merge-write tagging, the corrected duplicate semantics from the AC-12 discussion, the rollback test for empty groups) is right and worth keeping.

Good calls worth naming: dropping the ticket's two partial `UniqueConstraint`s after recognizing MySQL has no partial indexes (ADR 0002 Rejected Alternative 6 already documents the trap); following the updated AC rather than the ticket's stale Description on the all-null rule fields; preserving sibling competency tags through `tag_object()`'s replace-the-list semantics, with a test that exercises the same-taxonomy case where a naive implementation would actually lose data.

## Blocking

### B1. The PR does not merge into `main` and must be rebased

Mechanism: the PR is stacked on #846's branch as it stood before #846 was squash-merged (`a58d833`). Merging `main` into `pr-head` in a scratch worktree produced add/add conflicts in `src/openedx_learning/applets/cbe/rest_api/v1/{serializers,urls,views}.py`, `src/openedx_learning/applets/cbe/rules.py`, `tests/openedx_learning/applets/cbe/test_rules.py`, and `tests/openedx_learning/applets/cbe/test_views.py`, and content conflicts in `src/openedx_learning/applets/cbe/api.py`, `tests/openedx_learning/applets/cbe/conftest.py`, and `tests/openedx_learning/applets/cbe/test_api.py`. `main` also changed `rules.py` (the rule-profile permission now branches on scope and requires `rules.is_authenticated`), `conftest.py` (fixture docstrings and order), and added the `archived` field on both models (#716).

Fix: rebase onto `fd4300e`, re-resolving the nine files, then address B2 and B3, which only exist because `main` moved. After the rebase, note that `resolve_supplied_leaf_group()`, `create_leaf_group()`'s `get_or_create()` lookups, and `_reject_duplicate_criterion()` all ignore `archived`; #717 is filed to own that, so nothing more is required here beyond not implying archived-safety in docstrings.

### B4. The Tag row lock does not make group creation race-safe under `ATOMIC_REQUESTS`

This is the headline design claim of the commit message ("Group creation is made race-safe by locking the competency's Tag row") and of the `create_leaf_group` docstring (`api.py:125`), and it does not hold in the configuration the platform runs under.

Facts: Tutor's platform settings template sets `ATOMIC_REQUESTS: true` for the default database (`tutor/templates/apps/openedx/config/partials/auth.yml:16`), and edx-platform's own `cms/envs/test.py:89` does the same, so a Studio request runs as one InnoDB transaction. InnoDB REPEATABLE READ establishes a transaction's read snapshot at its first consistent (non-locking) read and serves every later consistent read from that snapshot; locking reads (`SELECT ... FOR UPDATE`) read the latest committed version instead. The author relied on exactly that second rule in `_reject_duplicate_criterion` (`api.py:222-228`, "Locking reads, so a duplicate committed by a concurrent request is seen under MySQL REPEATABLE READ") but not in `create_leaf_group`.

Mechanism: in this view the first consistent read happens long before the lock: authentication loads the user, `views.py:84` loads the Tag, `api.py:271-276` parse the key and load the CourseRun. Only then does `api.py:285` (and again `api.py:132`) take `Tag ... FOR UPDATE`. Take two requests A and B for the same tag and course with no groups yet. B blocks on the Tag lock until A commits, but B's snapshot predates A. `create_leaf_group` then calls `CompetencyCriteriaGroup.objects.get_or_create(...)` (`api.py:133`, `api.py:138`). Django 5.2.17's `get_or_create` (source printed during review) first runs a plain `self.get(**kwargs)`, a non-locking read served from B's stale snapshot, so B does not see A's root, creates a second root (nothing constrains roots on MySQL, as the PR itself notes), and then creates a second course-level group under that new root; the `(tag, course, parent)` constraint does not fire because `parent` differs. The tree invariant that #672 and #681 build on ("a course has at most one course-level group per competency") is silently broken. In the variant where the root already existed before both requests, B's course-level `create()` does hit the constraint; Django catches the `IntegrityError` and retries `self.get()`, which is again a non-locking read from the stale snapshot, raises `DoesNotExist`, and Django re-raises the `IntegrityError`: a 500. SQLite has neither row locks nor MVCC snapshots, so the suite cannot observe any of this, and the two "concurrent request" tests (`test_api.py`, pre-committing a root or course-level group out of band) only prove that a fresh-snapshot read finds a row.

Fix: make the two lookups locking reads so they see the latest committed state regardless of when the snapshot was taken: `CompetencyCriteriaGroup.objects.select_for_update().get_or_create(...)`. The `FOR UPDATE` clause carries into `get_or_create`'s internal `get()`, including the retry after an `IntegrityError`, so both failure modes above close. An explicit `select_for_update().filter(...).first()` followed by `create()` is equivalent and arguably clearer, since the Tag lock already serializes writers for the tag. Update the docstring at `api.py:125` and the comment at `api.py:130-131` to say that correctness depends on the lookups being locking reads under a stale snapshot, not on the lock preceding them. Add a test asserting `select_for_update` is applied to the group lookups (the existing `test_create_leaf_group_locks_the_tag_row_before_creating_groups` pattern works), since the race itself cannot be exercised on SQLite.

Confidence: the Django half is verified from the installed source; the InnoDB half is the documented behavior of the "Consistent Nonlocking Reads" and "Locking Reads" sections of the MySQL manual. I had no MySQL instance, so this was not executed.

### B5. AC scenario "A taxonomy-scoped rule profile is assigned ahead of the system default" is not implemented

Mechanism: when all three rule fields are omitted, `api.py:196-202` always fetches the single all-null (system default) `CompetencyRuleProfile`. The AC has two scenarios for this path: "no rule profile is scoped to that competency's taxonomy, then rule_profile_id is the system default", and "a competency whose taxonomy has its own rule profile, then rule_profile_id is that taxonomy's rule profile, not the system default". Probe G created a live profile with `competency_taxonomy = tag.taxonomy` and posted with no rule fields; the response carried the system default's id. There is no test for the taxonomy-scoped scenario, and the PR body's "One test per scenario in #665's Acceptance Criteria (all 20)" is therefore inaccurate. The commit message lists two developer-approved deviations from the ticket text and this is not one of them, so it reads as an oversight rather than a decision.

ADR 0002 Decision 4 defines the assignment: a course-scoped profile always wins, then organization versus taxonomy (resolved by `taxonomy_overrides_org`), then the system default. This endpoint has two of those contexts in hand, `course_run` and `tag.taxonomy`; organization scoping has no source yet (ADR 0002 Decision 4's MVP note). #672 says the frontend resolves against the system default only, and the ADR's MVP note says only the system default exists in this phase, so there is a real tension between the AC and the rest of the program. That is for the ticket owners to settle, but the PR cannot silently pick a side.

Fix: either implement the lookup (at minimum: a live profile with `competency_taxonomy_id = tag.taxonomy_id`, else the system default; following Decision 4's table in full by checking `course = course_run` first is the ADR-faithful version and costs one more query) with a test for each branch, or get the AC amended before merge and record the deviation in the commit message alongside the other two.

## Should fix

### S1. Unvalidated rule-field combinations produce 500s, and error keys are inconsistent

Mechanism: `CompetencyCriterionSerializer` (`serializers.py:59-89`) declares `rule_profile_id`, `rule_type_override`, and `rule_payload_override` independently with no cross-field validation, and `create_competency_criterion` (`api.py:206-212`) passes them straight to `CompetencyCriterion.objects.create()`. The model's `save()` runs `full_clean(validate_constraints=False)`, so the `profile_xor_override_check` constraint is only enforced by the database. Reproduced at the REST layer: `rule_profile_id` plus both overrides, and `rule_payload_override` alone, both raise `IntegrityError: CHECK constraint failed: oel_cbe_criterion_profile_xor_override_check` out of the view (a 500 in production). `rule_type_override` alone does return 400, but keyed `__all__` via the model's `clean()`, and an unknown `rule_profile_id` returns 400 keyed `rule_profile` (the model attribute, not the API field name). The AC asks that a 400 "identifies the invalid or missing field".

Fix: a serializer `validate()` that accepts exactly three shapes (no rule fields; `rule_profile_id` alone; both overrides together) and rejects everything else with a field-keyed message. Declaring `rule_profile_id` as `PrimaryKeyRelatedField(source="rule_profile", queryset=..., required=False, allow_null=True)` makes the unknown-id case a 400 keyed `rule_profile_id` and also solves S2. Keep the model-level `clean()` as the admin/test backstop it was designed to be (#613).

### S2. An archived rule profile is accepted

Mechanism: `serializers.py:80` is a bare `IntegerField`, so any existing profile id passes. Probe E posted the id of a profile created with `archived=True` and got 201 with that id persisted. ADR 0002 Decision 3: "Archived profiles are hidden from authoring and new associations." `get_competency_rule_profiles()` (`api.py:67-80`) already encodes the live-only rule.

Fix: `PrimaryKeyRelatedField(queryset=get_competency_rule_profiles(), ...)` as in S1.

### S3. Placeholder group names overflow the column, and the leaf is unnamed contrary to the AC

Mechanism: `CompetencyCriteriaGroup.name` is `max_length=255` (`models/criteria.py:79-81`), `Tag.value` allows 500 characters (`openedx_tagging/models/base.py:58-59`), and `CourseRun.title` allows 255 (`openedx_catalog/models/course_run.py:131-132`). `api.py:136` builds `f"{tag.value} (root)"` and `api.py:142` builds `f"{tag.value} — {course_run.title}"`. Probe L with a 500-character tag value produced names of 507 and 512 characters. SQLite stores them silently; MySQL in the strict mode Django requires raises `DataError` ("Data too long for column"), a 500 for any competency whose value is long. `CompetencyCriteriaGroup` has no `save()` override calling `full_clean()`, so nothing application-side catches it either. Separately, the leaf created at `api.py:144-149` sets no `name`, so it persists as `""` (probe K), while the AC's first scenario says the leaf is "named from the course's display name".

Fix: stop embedding `tag.value` in placeholder names (the tag id or uuid is stable and short; the group already carries the `tag` FK), or truncate to the column. For the leaf, set `name=course_run.title` per the AC, or get the AC amended; #672 notes the frontend deliberately ignores stored names, so this is for admin visibility, which the ticket's own Open Questions ask for.

### S4. `object_id` is not constrained to a course subsection; a library key crashes

Mechanism: `api.py:271-278` parses any `UsageKey` and passes `usage_key.course_key` to `get_course_run()`, which is `CourseRun.objects.get(course_key__exact=course_key)` (`openedx_catalog/api_impl.py:105-116`) on a `CourseKeyField`. For a V2 library key (`lb:Org1:lib1:problem:p1`), `course_key` is a `LibraryLocatorV2`, which is not a `CourseKey`; the field's lookup fails with `AssertionError: lib:Org1:lib1 is not an instance of <class 'opaque_keys.edx.keys.CourseKey'>` out of the view (probe I), a 500. Any block type is accepted: probe H got 201 for `type@problem` and for `type@course`, although the AC says a value that "doesn't parse as a subsection usage key" is a 400 and the ticket lists course-level association as explicitly out of scope. (The ticket deliberately excludes *gradeability* validation; checking the block type is a different, cheap check.)

Fix: validate in one place (see S5 for why the serializer is the right place): `UsageKey.from_string`, then `isinstance(key.course_key, CourseKey)` and `key.block_type == "sequential"`, each failure a 400 keyed `object_id`. Add a test for each.

### S5. Permission is checked before `object_id` is validated, which changes the production status code

Mechanism: `views.py:84-87` builds `ObjectTagPermissionItem(taxonomy=tag.taxonomy, object_id=data["object_id"])` and calls `has_perm("oel_tagging.can_tag_object", ...)` before `associate_competency_criterion` parses the key. In openedx-core's own rules the object-id predicate ignores the string, and the test module replaces it with a predicate that also ignores it, so the suite sees the 400. In the platform, `can_change_object_tag_objectid` (edx-platform `openedx/core/djangoapps/content_tagging/rules.py:228-232`) returns `False` when the string does not parse, so a malformed `object_id` yields 403 rather than the AC's 400 ("Reject creation with a missing or malformed object_id, then 400 and the body identifies the invalid field"). The ticket's Logic steps order parse (400), course (400), permission (403). Checking permission before revealing anything about a course is a defensible stance, but it is not the one the ticket chose, and the PR does not say it is deviating.

Fix: move `object_id` parsing and shape checks into the serializer (`validate_object_id`), so the permission check runs on a key known to be well-formed, and keep the CourseRun lookup in the API where it is. If the reverse order is preferred for security, say so in the PR and get the AC's status code adjusted.

### S6. Response field names match neither the AC nor the frontend ticket, and the PR body describes mappings the code lacks

Mechanism: the response keys are `group_id, id, object_tag_id, rule_payload_override, rule_profile_id, rule_type_override` (probe N). The AC's first scenario names `oel_tagging_objecttag_id`. #672 (updated 2026-09-21, after the 2026-09-15 ticket rename to `group_id`/`rule_profile_id`) says the frontend reads `competencyCriteriaGroupId` from the create response, i.e. `competency_criteria_group_id`. The PR body claims `competency_rule_profile_id`, `competency_criteria_group_id`, and `oel_tagging_objecttag_id` "mapped via explicit `source=`"; `serializers.py:70-89` has no `source=` and uses the short names, and its docstring says so. The request-side names (`object_id`, `group_id`, `logic_operator`, `rule_type_override`, `rule_payload_override`) do match #665, #671, and #672.

Fix: pick one response vocabulary with the ticket owners and the frontend before merge (the serializer change is a `source=` per field either way), then fix the PR body. If `group_id` is kept, #672 needs a one-word update.

### S7. `select_for_update()` on a missing `ObjectTag` row takes a gap lock, and concurrent first-time associations for different tags can deadlock

Mechanism: `api.py:223-225` runs `ObjectTag.objects.select_for_update().filter(object_id=..., taxonomy_id=..., tag_id=...).first()`. On a first association the row does not exist. InnoDB serves a locking read for a unique-index point lookup that finds no row by locking the gap where the row would be, and gap locks taken by two transactions on the same gap do not conflict with each other. Both transactions then try to insert their `ObjectTag` rows (through `tag_object()` at `api.py:193`); an insert needs an insert-intention lock on that gap, which does conflict with the other transaction's gap lock, so each waits on the other and InnoDB rolls one back with a deadlock error: a 500 for one author. The Tag row lock does not help here because the two requests are for different tags (the "same object, two competencies" case the AC calls out, or, in a sparse `oel_tagging_objecttag` table, any two first-time associations whose keys fall in the same wide gap). Reasoned from InnoDB's documented locking rules; not reproduced (no MySQL available).

Fix options, for the author and maintainers to weigh: (a) keep the Tag lock, make the duplicate check a plain read, and treat the `ObjectTag` `unique_together` on `(object_id, taxonomy, tag_id)` (`openedx_tagging/models/base.py:733-735`) as the race backstop by catching `IntegrityError` from `tag_object()` and returning the duplicate 400, accepting that under a stale snapshot the duplicate is caught by the constraint rather than the pre-check; or (b) keep the locking reads and document that a deadlock-induced 500 under concurrent first-time associations is expected and retried by the client. (a) is simpler and has no deadlock surface. Whichever is chosen, write it down next to the lock, because the next reader will otherwise re-derive it.

### S8. Public API surface is wider than the ticket intends, and `Http404` leaks out of the Python API

Mechanism: `__all__` (`api.py:28-38`) exports `resolve_competency_tag`, `create_leaf_group`, `resolve_supplied_leaf_group`, and `create_competency_criterion`, and `src/openedx_learning/api.py` re-exports them with a wildcard, making all four stable public contracts under CLAUDE.md's DEPR rule. `create_competency_criterion` called directly bypasses both the Tag lock and the duplicate check. `resolve_competency_tag` and `resolve_supplied_leaf_group` raise `Http404` (`api.py:111`, `api.py:114`, `api.py:159`); a repo-wide grep finds no other `Http404` or `get_object_or_404` in any `api.py` or model module, only in `rest_api/` views. The ticket's Technical Details did suggest `get_object_or_404` for the group lookup, so this is a reviewer's judgment rather than a ticket violation, but the ticket also names `associate_competency_criterion` as "the single public entry point".

Fix: underscore-prefix the helpers (tests can import them from `openedx_learning.applets.cbe.api`), or at minimum mark them UNSTABLE in their docstrings as `get_competency_rule_profiles` already is; raise `Tag.DoesNotExist` / `CompetencyCriteriaGroup.DoesNotExist` (or a small domain exception) from the API and map it to `NotFound` in the view, which is a two-line `except` next to the existing `DjangoValidationError` mapping at `views.py:98`.

### S9. The PR description and one test comment describe the earlier design

Mechanism: the PR body says two partial `UniqueConstraint`s in migration `0004`, `resolve_or_create_leaf_group()`, `source=` mappings, tests in `test_criteria_models.py`, and "two tests proving the constraints themselves exist". The code has one unconditional constraint in `0014`, `create_leaf_group()`, no `source=`, `test_criteria_group.py`, and one constraint test. `tests/openedx_learning/applets/cbe/test_criteria_group.py:52-57` was changed to use a second tag because "the one-root-per-tag constraint allows only one root group per tag"; no such constraint exists in the final PR (both groups in that test have `course` and `parent` null, so the shipped `(tag, course, parent)` constraint never applies), so the change is a leftover and the comment is false. `api.py:125` ("race-safe by locking") is also inaccurate until B4 is fixed. CLAUDE.md treats stale comments as bugs.

Fix: revert the `test_criteria_group.py` hunk; rewrite the PR body to describe the shipped mechanism, file names, and field names; fix the docstring with B4.

### S10. Test gaps

Beyond the tests B4, B5, S1, S3, and S4 each call for: (a) a 201 with a supplied override pair and the response echoing both fields (AC scenario 1 says the response includes "any supplied rule_type_override/rule_payload_override"; probe F shows it works, but nothing asserts it); (b) a 404 for a tag that exists on a non-competency taxonomy (AC "exists but is not a tag within a Competency Taxonomy"; probe J shows it works; `test_competency_not_found_404s` only covers a nonexistent id); (c) a 400 for each rejected rule-field combination (S1).

### S11. `tag_object()` raises `ValueError` for a single-tag taxonomy, surfacing as a 500 (low)

Mechanism: `create_competency_taxonomy()` accepts `allow_multiple=False`; `tag_object()` raises `ValueError("Taxonomy (...) only allows one tag per object.")` (`openedx_tagging/api.py:325-326`) when the merged list has two values. Probe M2: the second competency on the same subsection in such a taxonomy raised out of the view.

Fix: either reject the taxonomy up front in `resolve_competency_tag` (a competency taxonomy that forbids multiple tags per object cannot express two competencies on one subsection, which the AC requires), or catch `ValueError` from `tag_object()` and return a 400.
