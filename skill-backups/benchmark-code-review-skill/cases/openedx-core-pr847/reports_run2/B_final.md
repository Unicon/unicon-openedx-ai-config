### Strengths

- The layering is right. `CompetencyCriterionCreateView.create()` only shapes the request, resolves the tag, and checks the permission; `associate_competency_criterion()` owns the domain operation end to end inside one `transaction.atomic()`, and the four helpers it composes are each a readable unit. Everything new is declared in `__all__` and re-exported through `openedx_learning.api`.
- The concurrency reasoning for the duplicate check is careful: the Tag row lock is taken before `_reject_duplicate_criterion()` runs, the existence reads inside it are locking reads, and the code comment says why (a duplicate committed by a concurrent request is visible under MySQL REPEATABLE READ). The test `test_associate_competency_criterion_locks_the_tag_row_before_the_duplicate_check` pins that ordering.
- The decision not to back the duplicate check with a schema constraint is well argued in the commit message and honors the AC-12 correction in the ticket comments (a different explicit leaf returns 201 and both criteria share one ObjectTag), and `test_duplicate_association_supplying_a_different_existing_leaf_creates_a_second_criterion` proves it.
- The partial-index trap on MySQL is avoided and documented in `models/criteria.py:113-123`, consistent with ADR 0002 Rejected Alternative 6, and the constraint's existence is proven directly with an `IntegrityError` rather than inferred through `get_or_create()`.
- The tag read-merge-write is tested with two tags from the same taxonomy, which is the only arrangement that can expose `tag_object()`'s replace semantics; the test docstring explains that choice.
- `test_associate_competency_criterion_rolls_back_newly_created_groups_when_criterion_creation_fails` directly verifies the ADR 0002 rule against persisting empty groups.
- Tests hit the real database and the real URL resolver (`reverse("cbe:criterion-create", ...)`); nothing is mocked except the lock spies.
- The two deviations the commit message declares (system-default profile instead of all-null; no duplicate constraint) are each justified against ADR 0002 and the model's own check constraint.

Do not use `makemigrations --merge`; a renumber is the convention here and leaves a linear history.

#### Important (Should Fix)

2. **AC "A taxonomy-scoped rule profile is assigned ahead of the system default" is not implemented, not tested, and not declared as a deviation.** `api.py:197-202` always selects the row with all three scope columns null. Probe: with a taxonomy-scoped `CompetencyRuleProfile` present for the tag's taxonomy and no rule fields supplied, the criterion was assigned the system default (id 1) rather than the taxonomy profile (id 2). There is no view or API test for this scenario, while the PR body claims one test per AC scenario, "all 20". This is partly a plan problem: ADR 0002 Decision 4's MVP note says only the system default exists in this phase, while the ticket's AC (edited 2026-09-15) requires the taxonomy case. Either implement the Decision 4 lookup for the one scope this endpoint can know (the tag's taxonomy, with the course run also in hand) or get the AC removed explicitly; in both cases, stop claiming the scenario is covered.

3. **Root-group creation is not race-safe when the request runs inside an enclosing transaction (ATOMIC_REQUESTS), and the failure state is sticky.** `create_leaf_group()` at `api.py:133-142` finds the root and course-level groups with `get_or_create()`, which issues non-locking reads. Under InnoDB REPEATABLE READ, a consistent read uses the snapshot established by the transaction's first consistent read. With Django's `ATOMIC_REQUESTS` on, that snapshot is taken long before the Tag lock at `api.py:285` (session and user lookups, `resolve_competency_tag()`, `get_course_run()` all read first), so a request that waited on the lock still reads a snapshot in which the winner's root does not exist, and inserts a second root; nothing in the schema stops it (the one constraint is on `(tag, course, parent)`, and the two course-level groups have different parents, so it does not fire either). From then on `get_or_create(tag=tag, parent=None)` raises `MultipleObjectsReturned` for every derive-path request on that competency, a permanent 500 until someone cleans the data by hand. The commit message's claim that the lock alone makes group creation race-safe holds only when the lock is the transaction's first statement, which is true in the unit tests and false in a CMS request as I recall edx-platform and Tutor configure the default database (`ATOMIC_REQUESTS: True`); see Needs research. Fix: make the root and course-level existence reads locking reads, the same way `_reject_duplicate_criterion()` already does, for example `CompetencyCriteriaGroup.objects.select_for_update().filter(tag=tag, parent=None).first()` followed by `create()` when None, under the Tag lock that is already held. Add a comment saying why `get_or_create()` is not used.

4. **Rule-field combinations the serializer accepts but the model's check constraint rejects surface as 500s.** `CompetencyCriterionSerializer` (`serializers.py:59-89`) accepts `rule_profile_id`, `rule_type_override`, and `rule_payload_override` independently, and `CompetencyCriterion.save()` runs `full_clean(validate_constraints=False)`, so the `oel_cbe_criterion_profile_xor_override_check` constraint is only enforced by the database. Probe: `rule_profile_id` plus both overrides raised `IntegrityError`; `rule_payload_override` alone raised `IntegrityError`. DRF does not translate `IntegrityError`, so a client typo becomes a 500 and a traceback. Fix: a serializer `validate()` that enforces "either a profile with no overrides, or both overrides with no profile" and returns a field-level 400. (A nonexistent `rule_profile_id` already yields a 400 through `full_clean()`'s FK validation, and `rule_type_override` alone yields a 400 keyed `__all__`, so those two paths are fine.)

5. **An archived `rule_profile_id` is accepted.** Probe: a profile created with `archived=True` was accepted and assigned (`rule_profile_id=2`). `CompetencyRuleProfile.archived`'s own help text says it "hides a profile from authoring and from new associations", and ADR 0002 Decision 3 says the same; #846's list endpoint already filters archived rows out, so a client could only reach one by id. Fix: reject with a field-level 400 when the referenced profile is archived, in the same serializer `validate()` or in `create_competency_criterion()`.

6. **The read-merge-write can delete another competency's criterion when the taxonomy is disabled.** `create_competency_criterion()` computes the existing tag list with `get_object_tags()` (`api.py:190`), which excludes `taxonomy__enabled=False`, and then hands that list to `tag_object()` (`api.py:193`), which replaces the taxonomy's full ObjectTag set using an unfiltered read. When the taxonomy is disabled, the merge reads an empty list, `tag_object()` deletes the other competency's ObjectTag, and `CompetencyCriterion.object_tag` is `on_delete=CASCADE`, so that criterion disappears. Probe: after disabling the taxonomy and associating a second competency, the first criterion no longer existed. Through the REST endpoint, openedx-core's default `oel_tagging.can_tag_object` refuses a disabled taxonomy with a 403, so the view is shielded in this repo's own configuration, but the hazard lives inside `associate_competency_criterion()`, which is public API that any Python caller (and #717's follow-on work) can call directly. Fix: build the merge list from the same unfiltered query `tag_object()` uses (`ObjectTag.objects.filter(taxonomy_id=..., object_id=...)`), or refuse a disabled taxonomy in `resolve_competency_tag()`, or create the single ObjectTag directly instead of going through replace semantics.

7. **The permission check runs before `object_id` is parsed or its course resolved, reversing the ticket's step order and likely changing the status code in production.** `views.py:84-87` builds `ObjectTagPermissionItem(taxonomy, object_id=raw string)` and calls `has_perm()` before `associate_competency_criterion()` parses the key at `api.py:271` and resolves the course run at `api.py:276`. The ticket's Logic puts parsing (step 2) and course resolution (step 3) before the permission check (step 4). In this repo's tests the override predicate ignores the string, so the "malformed object_id is 400" tests pass; under openedx-platform's `can_tag_object`, which has to parse the object_id to find the course, an unparseable string most likely yields False, so the AC's 400 becomes a 403 (see Needs research). Fix: parse the usage key and resolve the course run before `has_perm()` (a `validate_object_id()` on the serializer is the natural place), then pass the parsed key down.

8. **`ValueError` from `tag_object()` is not caught, so an admin-configurable case is a 500.** Probe: with a competency taxonomy created with `allow_multiple=False`, the second competency associated to the same subsection raised `ValueError: Taxonomy (Single) only allows one tag per object.` `tag_object()` also raises `ValueError` when `OBJECT_MAX_TAGS` is exceeded. The tagging app's own `ObjectTagView` (`src/openedx_tagging/rest_api/v1/views.py:590-595`) maps both `ValueError` and `Tag.DoesNotExist` to a 400. Fix: catch `ValueError` around `tag_object()` in `create_competency_criterion()` and raise a field-level `ValidationError`, matching that precedent.

9. **The PR body describes a different implementation from the one in the commit.** A maintainer reading GitHub is told: two partial `UniqueConstraint`s including one root per tag (the code has one unconditional constraint and a row lock, and roots have no constraint at all); migration `0004` (it is `0014`); a function named `resolve_or_create_leaf_group()` (it is `create_leaf_group()`); response fields `competency_rule_profile_id`, `competency_criteria_group_id`, and `oel_tagging_objecttag_id` mapped via `source=` (the serializer emits `rule_profile_id`, `group_id`, and `object_tag_id` with no `source=`); `test_criteria_models.py` (it is `test_criteria_group.py`); "147 passed" (209 here). The most consequential of these is the concurrency description, because a reviewer would believe root uniqueness is database-enforced when it is not. Fix: replace the PR body with the commit message, which is accurate on all of these points except that it also names `resolve_or_create_leaf_group()`.

### Recommendations

- Consider asserting the lock-before-read ordering for `create_leaf_group()` the same way it is asserted for the duplicate check, once the reads become locking reads (finding 3).

- After the rebase onto main, `get_or_create()` will happily reuse an `archived=True` root or course-level group. That is #717's scope, but worth a sentence in the commit message so nobody files it as a bug against this PR.
