## 5. Task 3: what is needed to test ideas rather than packages (the DoorDash example)

DoorDash's production reviewer (acceptance 60% on high and critical findings; https://www.zenml.io/llmops-database/building-a-production-ai-code-review-agent-with-high-engineer-acceptance) combines: review-only rules mined from past reviews, each kept only with concrete file-and-line evidence in the codebase and routed by the paths a PR touches; a lead scout that flags suspicious areas without verifying, followed by deep reviewers that verify the leads; a "disprove-it" pass that drops any claim that cannot withstand scrutiny; full-repository access so the reviewer can trace callers and dependents; and dropping every comment without an action point. LangChain's ReviewBench (https://langchain.com/blog/evaluating-code-review-agents-with-reviewbench) adds that a structured "identify what changed, trace what depends on it, validate against callers, tests and related implementations" prompt beat model swaps. CR-Bench (https://arxiv.org/html/2603.11078v1) warns that recall-maximizing "look again" loops raise recall a few points and cut precision and usefulness hard; do not add those.

Work out and write down, as a plan the user can approve, what each idea needs before it can be benchmarked here:

- **Mined review rules.** A corpus of past maintainer review comments on openedx-core: `gh api` over closed PRs, their reviews and review comments, filtered to maintainers (at least `ormsbee`; ask the user for the list), with dates. A Sonnet pass turns comments into candidate rules ("X must / must never Y because Z"); a second pass keeps only rules that can be anchored to a current file and line; dedupe; route each rule by path prefix. Output is a candidate `review-rules.md` in the scratchpad, not in `.claude/`. Leakage guard: exclude PR 847's review and anything after 2026-10-11 from the corpus when the 847 case is the test, and say so in the results; the honest measurement needs held-out cases (next bullet).
- **More frozen cases.** Three to five openedx-core PRs with substantive maintainer reviews, chosen by `gh api` (reviews with CHANGES_REQUESTED by a maintainer, eight or more inline comments, merged), frozen with `scripts/freeze_pr.py` and given ground truth by the SKILL.md step 2 procedure. These cases are where the new ideas are judged; PR 847 becomes a regression check.
- **A scout-then-verify skill variant.** Draft `code-review-v3` in the scratchpad: a lead scout pass that lists suspicious areas with no verdicts; parallel deep reviewers, one per lead cluster, that verify leads by running code; a disprove-it pass per finding that must state what evidence would refute it and go look; a severity policy written from the project's merge bar (a 500 from a client-reachable input, a broken deploy or migration, a contradiction of an ADR or AC, a layering leak are blocking); the merge-with-main step and the premise audit from the failure classes above; no "Strengths" section. Serve it as files and benchmark it against v2 and the PR 49 skill on the held-out cases, tracking the count of confident wrong blocking findings as its own metric, since that was the costliest failure in run 2.
- **Cost and time to budget.** One variant run on this case took 10 to 30 minutes wall clock and roughly 250k to 500k tokens, or $5.49 for the built-in skill as reported by its own process; the rate limit killed a whole run set once (SKILL.md step 7 says how to resume).
